Esta es una variante muy interesante de la primera llamada que analizamos. La función de C sigue siendo **`sigprocmask()`** (o `pthread_sigmask()` en hilos), pero con una diferencia clave en cómo se está utilizando.

En este rastro, el programa no solo está bloqueando una señal, sino que está realizando un **intercambio de información**.

### Desglose del trace
`rt_sigprocmask(SIG_BLOCK, [CHLD], [INT], 8) = 0`

1.  **`SIG_BLOCK`**: El comando. Añade las señales del nuevo conjunto a las que ya estaban bloqueadas.
2.  **`[CHLD]`**: El **nuevo conjunto** a bloquear. El programa quiere bloquear `SIGCHLD`.
3.  **`[INT]`**: Esta es la parte clave. Es el **conjunto previo**. Indica que, antes de esta llamada, la señal `SIGINT` (Ctrl+C) **ya estaba bloqueada**. La función ha guardado ese estado anterior en la variable que le pasaste.
4.  **`8`**: Tamaño del tipo `sigset_t`.
5.  **`= 0`**: Éxito.

---

### Ejemplo de código en C
Para generar este rastro exacto, el código debe pasar un puntero al tercer argumento de `sigprocmask` para recuperar la máscara antigua:

```c
#include <signal.h>
#include <stdio.h>

int main() {
    sigset_t nuevo_set, antiguo_set;

    // Supongamos que SIGINT ya estaba bloqueado por alguna razón previa...
    
    // Configuramos el nuevo conjunto con SIGCHLD
    sigemptyset(&nuevo_set);
    sigaddset(&nuevo_set, SIGCHLD);

    /* Al pasar &antiguo_set como tercer argumento, 
       el kernel rellena esa variable con las señales 
       que estaban bloqueadas antes de esta línea.
    */
    if (sigprocmask(SIG_BLOCK, &nuevo_set, &antiguo_set) == 0) {
        // En este punto, el trace mostraría [INT] en el tercer parámetro
        // si SIGINT ya estaba bloqueada.
    }

    return 0;
}
```

### ¿Por qué se hace esto?
Este patrón es fundamental para escribir código robusto. Los programadores lo usan para:

1.  **Secciones Críticas:** Bloqueas una señal temporalmente para realizar una tarea importante.
2.  **Restauración:** Una vez terminada la tarea, usas esa variable `antiguo_set` para dejar el sistema exactamente como estaba, usando `sigprocmask(SIG_SETMASK, &antiguo_set, NULL)`.



Si no guardaras la máscara antigua (pasando `NULL` como hiciste en tu primera pregunta), podrías desbloquear accidentalmente señales que otras partes de tu programa necesitaban mantener bloqueadas, causando errores difíciles de encontrar.




La función de C que genera ese rastro es, una vez más, **`sigprocmask()`**, pero utilizada con el comando **`SIG_SETMASK`**.

A diferencia de `SIG_BLOCK` (que añade señales a la lista) o `SIG_UNBLOCK` (que las quita), `SIG_SETMASK` es un **"reset" total**.

### ¿Qué está haciendo exactamente?
En el rastro `rt_sigprocmask(SIG_SETMASK, [], NULL, 8) = 0`:

* **`SIG_SETMASK`**: Indica que quieres reemplazar la máscara actual de señales por una nueva.
* **`[]`**: Este es el nuevo conjunto de señales. Al estar vacío, significa que **estás desbloqueando todas las señales** que pudieran estar bloqueadas previamente.
* **`NULL`**: No te interesa guardar cuál era la máscara anterior.
* **`8`**: Tamaño del conjunto de señales.

En resumen: esta llamada le dice al sistema operativo: **"A partir de ahora, no bloquees ninguna señal; deja que todas lleguen al proceso normalmente"**.

---

### Ejemplo de código en C
Este rastro se genera típicamente al final de una sección crítica para restaurar el flujo normal del programa:

```c
#include <signal.h>

int main() {
    sigset_t vacio;
    sigemptyset(&vacio);

    // Esto genera: rt_sigprocmask(SIG_SETMASK, [], NULL, 8)
    sigprocmask(SIG_SETMASK, &vacio, NULL);

    return 0;
}
```

### ¿Por qué aparece esto en tu programa?
Es muy común ver esta llamada en dos situaciones:

1.  **Restauración tras sección crítica:** El programa bloqueó señales (como `SIGINT`) para hacer algo delicado y, al terminar, usa esta llamada para "limpiar" la máscara y volver al estado inicial.
2.  **Después de un `fork()`:** A veces, un proceso hijo hereda la máscara de señales de su padre. El hijo puede ejecutar esta llamada para asegurarse de que empieza su ejecución con todas las señales desbloqueadas.



### El "patrón sandwich"
Si miras tu `strace` completo, lo más probable es que veas algo así:
1.  `rt_sigprocmask(SIG_BLOCK, [CHLD], [INT], 8)` <--- **Bloquea** algo.
2.  *... (código del programa haciendo su trabajo) ...*
3.  `rt_sigprocmask(SIG_SETMASK, [], NULL, 8)` <--- **Libera** todo.

La función de C que genera ese rastro es el propio **manejador de señales (signal handler)** al terminar su ejecución.

A diferencia de las otras que hemos visto, **`rt_sigreturn()`** no es una función que tú llames explícitamente en tu código como `printf()` o `kill()`. Es una llamada al sistema "especial" que el kernel de Linux inserta automáticamente para limpiar todo después de que tu manejador de señales ha terminado de ejecutarse.

### ¿Qué está pasando exactamente?

Cuando llega una señal y el proceso tiene un manejador configurado, ocurre lo siguiente:

1.  **Interrupción:** El kernel detiene la ejecución normal de tu programa.
2.  **Cambio de Contexto:** El kernel guarda el estado actual (registros de la CPU, pila, etc.) y salta a la función que tú definiste como manejador.
3.  **Ejecución:** Tu función (el manejador) se ejecuta.
4.  **El retorno:** Cuando tu función llega al final (`return` o la llave de cierre `}`), el control debe volver al punto exacto donde el programa fue interrumpido.

Ahí es donde entra **`rt_sigreturn()`**. El kernel prepara un "trampolín" de código que invoca esta llamada al sistema para restaurar el estado original del proceso y desbloquear las señales que se habían pausado.

---

### Ejemplo de código en C

Cualquier programa que use un manejador de señales generará este rastro cada vez que reciba la señal:

```c
#include <signal.h>
#include <stdio.h>
#include <unistd.h>

// Cuando esta función termine, se generará el rt_sigreturn()
void mi_manejador(int sig) {
    printf("¡Señal recibida!\n");
}

int main() {
    struct sigaction sa;
    sa.sa_handler = mi_manejador;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;

    sigaction(SIGINT, &sa, NULL);

    printf("Esperando Ctrl+C...\n");
    while(1) pause();

    return 0;
}
```

### ¿Cómo se ve en el flujo de `strace`?

Si ejecutas el código de arriba y presionas Ctrl+C, verás esta secuencia:

1.  `--- SIGINT {si_signo=SIGINT, ...} ---` (Llega la señal).
2.  `write(1, "¡Señal recibida!\n", ...)` (Se ejecuta tu código dentro del manejador).
3.  **`rt_sigreturn({mask=[]}) = 0`** (El sistema limpia y restaura el programa).
4.  `pause() = ? ERESTARTSYS ...` (El programa vuelve a lo que estaba haciendo).



### Resumen
* **¿Quién la llama?** El kernel de Linux, automáticamente, cuando una función manejadora de señales termina.
* **¿Para qué sirve?** Para restaurar el proceso a su estado original antes de la interrupción.
* **¿Por qué es `rt_`?** Al igual que las anteriores, es la versión "Real Time" que soporta los conjuntos de señales modernos en Linux.




que genera esto en el strace ERESTART_RESTARTBLOCK (Interrupted by signal)

Este mensaje en `strace` no es generado por una función de C específica, sino que es un **mecanismo interno del kernel de Linux** para manejar llamadas al sistema que duran mucho tiempo y fueron interrumpidas por una señal.

Aparece cuando una función (como `nanosleep` o `poll`) es interrumpida, pero el sistema quiere intentar **recomenzar la espera** automáticamente sin que el programador tenga que escribir un bucle manual.

### ¿Qué está pasando exactamente?

1.  **La Interrupción:** Tu programa estaba ejecutando una llamada al sistema de "bloqueo" (por ejemplo, durmiendo por 10 segundos).
2.  **La Señal:** Llega una señal (como `SIGINT` o `SIGCHLD`). El kernel detiene la llamada al sistema para ejecutar el manejador de señales.
3.  **El Dilema:** Una vez que el manejador termina (`rt_sigreturn`), el kernel tiene dos opciones:
    * Devolver un error `-1` y poner `errno = EINTR`.
    * **Reiniciar la llamada** para que termine el tiempo que le faltaba.
4.  **El Restart Block:** Para llamadas que dependen del tiempo (timers), el kernel usa un "Restart Block" para recordar cuánto tiempo quedaba pendiente y retomar la cuenta exactamente donde se quedó.

---

### ¿Qué funciones de C suelen provocar esto?

Principalmente funciones que involucran **esperas de tiempo precisas** o **bloqueos de red**:

* `nanosleep()`
* `clock_nanosleep()`
* `poll()` / `ppoll()`
* `select()` / `pselect()`
* `futex()` (usado internamente por `pthread_cond_wait`)

### Ejemplo de flujo en `strace`

Si tienes un `nanosleep` de 5 segundos y presionas Ctrl+C al segundo 2, verás esto:

```bash
nanosleep({5, 0}, 0x7ffd...) = ? ERESTART_RESTARTBLOCK (Interrupted by signal)
--- SIGINT {si_signo=SIGINT, ...} ---
rt_sigreturn({mask=[]}) = 0
# Aquí el kernel usa el "restart block" para dormir los 3 segundos restantes
restart_syscall(<... resuming read ...>) = 0 
```

### ¿Por qué lo ves tú?

Si este rastro aparece y tu programa **continúa** funcionando normalmente, es una buena señal: significa que el kernel y la librería de C están gestionando las interrupciones por ti de forma transparente.

Si el programa **falla** o se detiene ahí, es posible que:
1.  La señal no tenga un manejador configurado.
2.  Hayas configurado la señal con el flag `SA_RESTART` desactivado, lo que obliga a la función a devolver un error en lugar de reiniciarse.



### Diferencia clave: `ERESTARTSYS` vs `ERESTART_RESTARTBLOCK`
* **`ERESTARTSYS`**: Se usa para funciones que simplemente pueden volver a empezar desde cero (como leer de un disco).
* **`ERESTART_RESTARTBLOCK`**: Se usa para funciones de tiempo. El kernel guarda el "tiempo restante" en una estructura especial porque no sería correcto volver a empezar el temporizador desde cero.
